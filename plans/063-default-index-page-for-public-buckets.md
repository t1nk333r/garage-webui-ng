# 063 — A default index page for public buckets, removable without closing access

**Status:** TODO · **Priority:** P2 · **Effort:** M · **Risk:** MED · **Depends on:** —
**Stamped against:** `main` `41f1030` (v3.9.1), 2026-08-31.

## The problem

Turning on **Website access** for a bucket (`overview-website-access.tsx`) sets
`websiteConfig.indexDocument`, default `"index.html"`. Garage then serves that
object for a request to the bucket root. If the object does not exist — the
normal case for a bucket that was filled by `aws s3 cp` or by this UI — the
public site answers **404 on its own root** while every direct object URL works
fine. The section already detects this: `useObjectExists` probes the configured
index and renders a "missing" state. It tells the user about the hole and then
offers nothing to fill it.

Garage has **no server-side directory listing**. There is no `autoindex`
equivalent, and anonymous callers cannot `ListObjectsV2` — website access grants
anonymous *object reads only*. So the only way a public bucket can have a
working root is for a real `index.html` object to exist in it.

The second half of the request follows from the first: once the UI can *place*
that object, the user must be able to **take it away again without disabling
website access**. Those are two independent switches today only by accident, and
the obvious naive implementation (clearing `indexDocument`) conflates them —
Garage treats an empty `indexDocument` as "use the default", not "no index".

## What we are building

A **Default index page** control nested inside the existing Website Access
section, with three states and one hard safety rule.

```
Website access                          [ON ]
  Index document      [ index.html            ]  ✓ found
  Error document      [ error/400.html        ]  ⚠ missing
  ┌────────────────────────────────────────────┐
  │ Default index page          [ON ]          │
  │ Generated by Garage WebUI-NG · 2026-08-31  │
  │ Lists 214 objects · [Regenerate]           │
  └────────────────────────────────────────────┘
```

- **ON** → a generated `index.html` exists at the configured index key and
  carries our provenance marker.
- **OFF** → the object is gone. `websiteAccess` stays `true`, so every direct
  object URL keeps working; only the bucket root 404s. This is the "stop the
  index without shutting access" requirement, and it is the *whole* behaviour:
  we delete one object and touch nothing else.
- **Unavailable** → an `index.html` exists that we did **not** generate. The
  toggle is disabled and reads *"This bucket has its own index.html — Garage
  WebUI-NG will not replace or delete it."*

### The safety rule (non-negotiable)

**Never write over, and never delete, an index object this tool did not
create.** A hand-written site index is user data. Provenance is an S3 user
metadata key set at PUT time:

```
x-amz-meta-garage-webui-ng-generated: 1
```

Every write checks `HeadObject` first and refuses if the object exists without
the marker. Every delete re-checks the marker immediately before `DeleteObject`
and refuses if it is absent — a TOCTOU-narrow re-read, not a cached value from
the page load. A missing marker is always "refuse", never "assume ours".

### What the generated page contains

A **static snapshot listing** of the bucket at generation time: object key,
size, last-modified, each linking to the object relative to the site root. Self
contained — inline CSS, no scripts, no external fetches (it is served from the
bucket's own origin under the site's CSP, and `plan 043` established that this
project does not ship inline script).

It is a snapshot, and **it goes stale the moment anything is uploaded**. That is
inherent: a live listing is impossible without anonymous `ListObjects`, which
would mean granting a far broader permission than website access. The plan
handles staleness by being honest about it rather than hiding it:

- the page footer carries the generation timestamp, visible to visitors;
- the UI shows *"Lists N objects · generated <when>"* and a **Regenerate**
  button;
- when the browse view's object count differs from the recorded count, the
  section shows *"This bucket has changed since the index was generated."*

**STOP condition for the executor:** do not attempt to make the listing live —
no client-side `ListObjectsV2` from the generated page, no embedded credentials,
no presigned listing URL. If you believe you have found a way, stop and write it
up instead of building it.

## Backend

One new route, registered next to the other browse routes in
`backend/router/router.go` (`:55-61`):

```go
router.HandleFunc("PUT /browse/{bucket}/index-page", browse.PutGeneratedIndex)
router.HandleFunc("DELETE /browse/{bucket}/index-page", browse.DeleteGeneratedIndex)
router.HandleFunc("GET /browse/{bucket}/index-page", browse.GetGeneratedIndexStatus)
```

**Route-shadowing check.** `GET /browse/{bucket}/{key...}` already exists at
`:58`. Go's `http.ServeMux` prefers the more specific pattern, so a literal
`index-page` segment wins over `{key...}` — but that means **an object actually
named `index-page` at the bucket root becomes unreachable through the API.**
Verify this with a test that PUTs an object called `index-page` and asserts the
existing `GetOneObject` path still serves it; if it does not, move the three
routes under a separate prefix (`/index-page/{bucket}`) exactly as plan 061 did
for `/search/{bucket}`, and say so in the plan row.

- `PutGeneratedIndex` — builds the HTML server-side (the listing data is already
  available through the same paginated walk `GetObjects` uses), then
  `HeadObject` on the target key; if it exists without the marker, respond
  **409** with a message the UI can show verbatim. Otherwise `PutObject` with
  `ContentType: "text/html; charset=utf-8"` and the metadata marker. Note
  `PutObject` at `browse.go:272` does **not** currently set `Metadata` — this
  handler must, which is why it is a separate handler rather than a flag on the
  existing upload path.
- `DeleteGeneratedIndex` — `HeadObject`, refuse with **409** unless the marker
  is present, then `DeleteObject`. **Does not touch `UpdateBucket`.** The
  bucket's `websiteAccess` and `indexDocument` are deliberately left exactly as
  they were; that is what makes this "stop the index without closing access".
- `GetGeneratedIndexStatus` — `HeadObject` → `{exists, generated, generatedAt,
  objectCount}` from the marker and metadata. 404 from Garage is a normal
  answer (`{exists:false}`), not an error.

**Authorization.** PUT and DELETE are writes: they must be denied to `viewer`.
Confirm `isViewerAllowed` in `backend/middleware/auth.go` rejects them — the
allowlist is verb-and-path based, so a new path needs checking, not assuming.
Add a middleware test for both verbs as a viewer.

**Key choice.** Generate at the bucket's *currently configured*
`indexDocument`, not a hard-coded `index.html`. If that field is empty, use
`index.html` and save it back so the two never disagree.

## Frontend

- `overview-website-access.tsx` gains a `<DefaultIndexSection>` child, rendered
  only when `websiteAccess` is true. It must not participate in the debounced
  auto-save `form.watch` — like the `websiteAccess` toggle itself (`:80-84`),
  it drives its own mutations explicitly.
- Three hooks in `manage/hooks.ts` following the one-hook-per-endpoint rule:
  `useGeneratedIndexStatus` (query key `["index-page", bucketName]`),
  `useGenerateIndexPage`, `useRemoveIndexPage`. Mutations spread `...options`
  last and invalidate both `["index-page", bucket]` and
  `["object-exists", bucket, indexDoc]` so the existing presence badge updates.
- Turning the toggle **off** needs no confirmation — same reasoning as
  `onToggleWebsiteAccess`'s comment at `:99`, disabling is the safe direction.
  Turning it **on** publishes a list of every object name to anonymous readers,
  which is a disclosure the user may not expect from a bucket whose objects were
  previously only reachable by exact key. **Reuse `PublicAccessConfirm`'s
  pattern** with wording that says exactly that.
- The 409 refusal must render as its own state, not a generic error toast.

## Verification gates

1. `cd backend && go build ./... && go vet ./... && test -z "$(gofmt -l .)" && go test -race ./...`
2. `pnpm run typecheck && pnpm run test && pnpm run build`
3. New Go tests on the existing `newS3Fixture` (plan 055): generate into an empty
   bucket; generate when a *marked* index exists (overwrites); generate when an
   *unmarked* index exists (**409, object byte-identical afterwards**); delete a
   marked index; delete an unmarked index (**409, object still present**);
   delete when absent; both writes as a `viewer` (**403**).
4. **Mutation test the safety rule**: delete the marker check in
   `DeleteGeneratedIndex` and confirm the unmarked-delete test fails. If it still
   passes, the test is not testing what it claims.
5. Frontend tests: the toggle is disabled with the explanatory copy in the
   unmarked state; turning it off calls the delete endpoint and **not**
   `UpdateBucket` (assert the mutation for `/v2/UpdateBucket` is never fired —
   this is the requirement, so it gets a direct assertion).
6. Manual, on a real cluster: enable website access, generate, load the site
   root anonymously, toggle the index off, confirm the root 404s **and a direct
   object URL still returns 200**.
